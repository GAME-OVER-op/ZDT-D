# AGENTS.md — инструкция для AI-ассистента

Этот файл — обязательная инструкция при работе над проектом ZDT-D. Ассистент должен прочитать её перед началом любой задачи и следовать ей на протяжении всей работы.

## Общие правила общения и работы

1. **Не делать изменения самостоятельно, если предварительно требуется обсуждение.** Любая правка кода, конфигурации или инфраструктуры начинается только после того, как план озвучен и подтверждён пользователем. Исключение — правки, которые пользователь прямо попросил выполнить в текущем сообщении.
2. **Сначала анализировать проблему, затем предлагать решение.** Порядок фиксированный: изучить код и факты → объяснить причину → предложить вариант → дождаться подтверждения → применять.
3. **Не выполнять потенциально опасные действия без понимания их последствий.** К опасным относятся изменение workflow'ов, скриптов сборки, module.prop, signing/keystore, системных служб, сетевых правил, а также любые действия с неясным результатом.
4. **Не удалять, не перезаписывать и не перемещать важные данные без согласования.** Это касается файлов, директорий, коммитов, веток и настроек окружения.
5. **Проверять результат каждого существенного действия.** После правки — посмотреть diff; после сборки — прочитать реальный вывод; после коммита — проверить, что запушено именно то, что планировалось.
6. **Не выдавать предположения за проверенные факты.** Гипотеза должна называться гипотезой. Утверждение «это работает» допускается только после проверки.
7. **Не считать задачу выполненной только потому, что команда завершилась без очевидной ошибки.** Успешный exit code не доказывает корректность поведения — проверяется результат, а не сам факт запуска.
8. **При диагностике опираться на реальные выводы команд, журналы и состояние системы.** Не строить выводы на предположениях о том, «как обычно бывает».
9. **Не повторять уже выполненные проверки без необходимости.** Результат предыдущей проверки в рамках текущей задачи считается действительным, пока не изменился код или окружение.
10. **Учитывать предыдущие решения и не заставлять пользователя заново объяснять контекст.** История работы и уже принятые решения — часть входных данных.
11. **Не вмешиваться в работающие процессы без необходимости.** Не останавливать сборки, сервисы и фоновые задачи, если это не требуется задачей.
12. **При возможности сохранять текущую рабочую конфигурацию и исправлять только конкретную проблему.** Минимальный точечный diff предпочтительнее широкой переделки.

## Дополнение: контекст и ограничения проекта

Следующие пункты конкретизируют общие правила применительно к ZDT-D и дополняют их.

### Язык и стиль ответа

- Отвечать по-русски по умолчанию. Другой язык использовать только по прямой просьбе (например, английская документация или строки UI).
- Отчёт после изменений: коротко перечислить, что изменено, почему это безопасно, какую проверку запускали и что проверить не удалось.

### Порядок работы над задачей

1. Изучить релевантные файлы и структуру проекта.
2. Кратко изложить найденное.
3. Объяснить предлагаемое изменение и его риск.
4. Дождаться подтверждения пользователя.
5. Применить только подтверждённые изменения.
6. Выполнить только запрошенную или явно безопасную проверку.
7. Сообщить точный результат.

### Область изменений

- Изменения — только по обсуждённой теме. Не делать массовое форматирование, широкие рефакторинги и «попутную» уборку без просьбы.
- Исправлять первопричину, а не только видимый симптом.
- Не удалять функции, не переименовывать пакеты, модули, API-маршруты, бинарники, workflow'ы и публичные ключи конфигурации без явной просьбы.
- Не добавлять телеметрию, аналитику, трекинг и новые внешние сетевые вызовы.
- Не трогать секреты, keystore, сертификаты, signing-конфигурацию и приватные ключи.

### Высокорисковые пути (изменять только после явного обсуждения)

- `.github/workflows/build.yml` и остальные workflow'ы релизов;
- `build.sh`, `module.prop`;
- `module_template/service.sh`, `customize.sh`, `uninstall.sh`;
- `zygisk/**`;
- `rust/zdtd/src/api.rs`, `runtime.rs`, `vpn_netd.rs`, `rust/zdtd/src/iptables/**`;
- логику релизов, версий/versionCode, подписи и prebuilt-бинарников;
- `keystores/**`, `prebuilt/**`.

Перед изменением любого из этих путей объяснить причину, точный объём и ожидаемое поведение после правки.

### Проверка и сборка

- Полные сборки (`build.sh`, release-скрипты, Gradle, `cargo build/check`) не запускать без прямой просьбы.
- Разрешённые проверки: поиск по коду, чтение нужных фрагментов, проверка наличия файлов, `unzip -t` для архивов и другая безопасная проверка, соответствующая задаче.
- GitHub CI не проверять без просьбы пользователя — пользователь делает это сам и сообщит результат, если понадобится.
- Если пользователь просит сборку или коммит/пуш — использовать личность, настроенную пользователем. GitHub самостоятельно генерирует релиз при изменении версии.

### Отладка на устройстве

- Для отладки доступен root `adb shell`. Только читать логи и состояние устройства; любые изменяющие действия (перезапуск сервисов, правка файлов, установка) — только по прямой просьбе.
- Если нужен воспроизводимый crash — попросить пользователя воспроизвести его и прислать свежий лог, а не пытаться угадать причину.

### Политика по Happ-подпискам

- Не переносить встроенные ключи дешифрования, HWID-spoofing и Xposed-разблокировку.
- Допускается только легальная поддержка форматов подписок.

### История и коммиты

- Писать понятные сообщения коммитов на английском, например `AI polish(ui): simplify app selection helper`.
- В теле коммита указывать: что изменено, почему это безопасно, какая проверка запускалась.
- Формат коммита и ветки сохранять прежними; не переписывать историю без просьбы.
